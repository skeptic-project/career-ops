# Task 001.02: Reference Local JD Files From Pipeline Entries

## Epic

[Epic 001: Persist Job Descriptions and Link Them Across Career-Ops](001-jd-persistence-pipeline-integrity.md)

## User Story

As a user processing pending jobs, I want `data/pipeline.md` to reference the local JD file so the pipeline evaluates stable local content instead of depending on a live external URL.

## Requirements

- Add pipeline entries in this format:

```markdown
- [ ] local:jds/<company-name>-<role>.md | Atlan | Engineering Manager
```

- Preserve company and role fields after the local path.
- Preserve existing optional columns after role where available, currently location and compensation from `formatPipelineOffer()`.
- Avoid duplicate pending entries for the same company, role, and JD path.
- Keep existing external URL entries compatible during migration.
- Update scanner dedup so a local JD pipeline entry still dedups the original source URL when that source URL is available from the JD metadata.

## Implementation Notes

- Update `scan.mjs` `formatPipelineOffer(offer)` to prefer `offer.jdPath`:
  - with JD: `- [ ] local:<jdPath> | <company> | <title> | <location?> | <compensation?>`
  - without JD: preserve current URL-based behavior.
- Update `loadSeenUrls()` to parse existing `local:jds/...` rows, read their source URL metadata when available, and add that source URL to the `seen` set.
- Keep URL-based rows supported because old `data/pipeline.md` files and manually pasted URLs must continue to work.
- Add tests near existing `formatPipelineOffer()` and `appendToPipeline()` coverage in `test-all.mjs`.

## Acceptance Criteria

- New scan output can add local JD references to `data/pipeline.md`.
- Auto-pipeline can consume `local:jds/...` entries without re-fetching the external posting.
- Duplicate prevention handles the local JD path format.
- Existing URL rows, location columns, and compensation columns continue to pass current tests.
