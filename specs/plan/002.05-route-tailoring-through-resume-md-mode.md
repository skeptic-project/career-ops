# Task 002.05: Route Tailored Markdown Generation Through resume-md Mode

## Epic

[Epic 002: Tailored Resume Markdown Support](002-tailored-resume-markdown.md)

## Problem

When `career-ops` evaluates a job URL and decides to generate a tailored Markdown resume, the current scripted path uses `resume-md-core.mjs`. That implementation performs a deterministic keyword pass and appends one sentence to the `## Professional Summary` block. It does not execute the richer `modes/resume-md.md` instructions that require JD-aware tailoring, exact `cv.md` preservation, and targeted string replacements.

This creates a behavior gap:

- `modes/resume-md.md` describes an LLM-guided tailoring workflow.
- `resume-md-core.mjs` implements a lightweight local keyword-tailoring workflow.
- Auto-pipeline currently depends on the script path when it needs a Markdown resume before PDF generation.

## Feasibility Assessment

Feasible, but it requires changing the execution boundary between agent modes and deterministic scripts.

`modes/resume-md.md` is an agent instruction file, not executable JavaScript. A Node script cannot directly "use the mode" unless the system invokes an LLM/agent runner or an equivalent structured tailoring service.

The product direction should be: **tailored resume Markdown is an agent-mode capability, not a keyword-script capability.** If a flow claims to generate a tailored resume, it must execute the `resume-md` mode instructions and use LLM judgment to decide what to change. Deterministic code may support the workflow, but it should not generate the tailored content itself.

Recommended direction:

1. Make `resume-md` mode the only content-tailoring path.
2. Refactor deterministic code into support utilities only:
   - resolve and save JD files;
   - extract company/role metadata;
   - load `cv.md`;
   - validate that output preserves Markdown structure;
   - apply a replacement plan generated by the agent;
   - write output files;
   - calculate/store scores and tracker fields.
3. If an agent/LLM runtime is unavailable, fail with a clear actionable error instead of silently producing a weak keyword-tailored resume.
4. For headless/batch usage, introduce an explicit LLM-backed worker path rather than a deterministic fallback. The user should be able to choose whether batch runs spend tokens; if they disable LLM tailoring, the system should skip `resume-md` generation rather than produce a misleading "tailored" file.

## User Story

As a career-ops user, when I evaluate a job URL and the command generates a tailored Markdown resume, I want it to use the same `resume-md` mode workflow that direct `career-ops resume-md` uses, so the Markdown resume is genuinely tailored rather than just receiving a generated summary sentence.

## Requirements

- Identify every flow that generates a tailored Markdown resume:
  - direct `career-ops resume-md`;
  - URL auto-pipeline;
  - pipeline mode;
  - batch/headless runners;
  - PDF generation paths that first create `resume-md`.
- Update auto-pipeline behavior so Markdown resume generation is routed through `modes/resume-md.md` whenever an agent runtime is available.
- Preserve the existing contract:
  - use `cv.md` as the exact base;
  - preserve Markdown formatting, whitespace, heading levels, and structure;
  - apply only targeted string replacements;
  - save output at `output/cv-{candidate}-{company}.md`;
  - calculate and store `final-score`;
  - populate tracker TSV `resume-md` and `final-score` columns.
- Remove deterministic keyword tailoring as a valid resume generation path for job applications.
- Refactor or replace `resume-md-core.mjs` so it no longer appends JD keywords to `## Professional Summary`.
- Introduce a structured replacement-plan contract between the agent mode and the filesystem writer:
  - `before`: exact text copied from `cv.md`;
  - `after`: replacement text;
  - `reason`: JD requirement addressed;
  - `source`: CV/JD evidence used;
  - `risk`: whether the replacement could overstate a claim.
- Validate every replacement before writing:
  - `before` must exist exactly once in `cv.md`;
  - heading order must remain unchanged;
  - no new top-level sections unless explicitly approved by the mode;
  - no unsupported claims or metrics outside source-of-truth files.
- Add clear logging or report notes indicating that the Markdown resume was generated by `resume-md` agent mode.
- Fix JD metadata expectations so local JD files include parser-friendly metadata:
  - `- Company: {company}`;
  - `- Role: {role}`;
  - `- Source URL: {url}`.
- Avoid recursive agent spawning or unbounded research. The `resume-md` mode must only tailor the resume from already-loaded JD, `cv.md`, and profile context.

## Product Decisions

- Batch/headless mode must not silently spend LLM tokens for resume tailoring. It should generate tailored Markdown only when an explicit LLM-tailoring mode/flag is selected by the caller.
- `node resume-md.mjs` should stop generating tailored content directly. It should either:
  - run only in an agent-backed context; or
  - become a validator/writer that requires an explicit replacement-plan JSON file generated by the agent.
- Add or repurpose a deterministic writer script, such as `apply-resume-plan.mjs`, to own safe file writes while the agent owns content decisions.
- `final-score` should be produced by the full A-G evaluation against the tailored resume in agent-backed flows. Keyword coverage may remain only as an internal diagnostic, not the canonical `final-score`.

## Implementation Notes

- Update `modes/resume-md.md` to define the replacement-plan contract explicitly and require the agent to produce/edit through that plan.
- Update `modes/auto-pipeline.md` Step 2.5 to say it must execute the `resume-md` mode workflow, not call deterministic keyword tailoring.
- Update `modes/pdf.md` if needed so PDF generation consumes the tailored Markdown created by the `resume-md` mode.
- Refactor `resume-md-core.mjs`:
  - remove `createTargetedReplacements()` keyword-sentence behavior as a production tailoring path;
  - keep reusable utilities for slugging, input/JD resolution, path building, scoring diagnostics, and safe replacement application;
  - add validation that each `before` string appears exactly once.
- Update `resume-md.mjs` so direct script usage does not imply LLM-grade tailoring unless an agent-produced replacement plan is supplied.
- Update `openrouter-runner.mjs` because it currently imports `writeTailoredResumeMarkdown()` and uses deterministic tailoring in both evaluate and direct `resume-md` paths.
- Add tests in `test-all.mjs` for:
  - rejecting deterministic keyword-only tailoring as a production resume output path;
  - applying an agent replacement plan without changing heading order;
  - refusing ambiguous replacements where `before` appears zero or multiple times;
  - preserving tracker compatibility for `resume-md` and `final-score`.

## Out Of Scope

- Building a new generic LLM orchestration framework.
- Rewriting the entire resume from scratch.
- Allowing batch/headless mode to spend tokens without an explicit opt-in.
- Treating keyword coverage as the canonical final-score in agent-backed flows.

## Acceptance Criteria

- In an interactive `career-ops <job-url>` run, the generated tailored Markdown resume is produced through the `resume-md` mode workflow, not by only appending a keyword sentence from `resume-md-core.mjs`.
- The generated Markdown file still preserves the base `cv.md` structure and only changes targeted text blocks.
- Tracker rows continue to include valid `resume-md` and `final-score` values.
- If agent-mode tailoring is unavailable, the pipeline does not create a tailored Markdown resume and records a clear pending/error state instead of producing a keyword-appended file.
- Regression tests or smoke checks cover both paths:
  - agent-mode orchestration selected for interactive auto-pipeline;
  - no-agent/headless execution fails or skips resume-md generation clearly without creating a misleading tailored resume.
