# Task 001.01: Persist Extracted JD Markdown

## Epic

[Epic 001: Persist Job Descriptions and Link Them Across Career-Ops](001-jd-persistence-pipeline-integrity.md)

## User Story

As a career-ops user, I want every scanned or URL-evaluated job description saved as a local Markdown file so future reports and tracker rows can point to the exact JD that was evaluated.

## Requirements

- Create `jds/` if it does not exist.
- Generate deterministic slugs from company and role: `jds/<company-name>-<role>.md`.
- Save the extracted job description for:
  - `career-ops scan`
  - `career-ops <job-description-url>`
- For `scan`, persist the JD after filtering/dedup/liveness and before `appendToPipeline()`/`appendToScanHistory()`.
- Use provider-supplied description fields when present; otherwise perform a bounded JD extraction from the job URL.
- Do not save title-only stubs as successful JD captures. If extraction fails, preserve the source URL and mark the JD path unavailable rather than pretending a full JD exists.
- Include source metadata in the Markdown file:
  - Company
  - Role
  - Source URL
  - Date captured
  - Extraction method, if available
- Keep the original source URL in the Markdown even when downstream pipeline entries use `local:jds/...`.
- Avoid overwriting a materially different JD without either versioning or deterministic conflict handling.

## Implementation Notes

- Add a shared helper such as `jd-store.mjs` with `slugifyJob()`, `writeJobDescriptionMarkdown()`, and `persistJobDescriptionForOffer()`.
- Expected slug normalization: lowercase, ASCII where possible, trim punctuation, collapse whitespace/punctuation to `-`.
- Conflict handling should be deterministic, for example:
  - same company/role/source URL and same normalized JD content: reuse the existing path;
  - same company/role but materially different content/source: write a suffixed path such as `jds/<slug>-<source-or-hash>.md`.
- Auto-pipeline URL mode should call the same helper after Step 0 extraction succeeds and before report/tracker generation.
- Scan mode should update each offer object with `jdPath` after persistence so later pipeline and history writers can consume it.

## Acceptance Criteria

- Running scan or URL auto-pipeline stores a readable Markdown JD under `jds/`.
- Re-running the same posting is idempotent.
- The stored JD contains enough metadata to trace the source URL and capture date.
- A scan result without extractable JD content does not create a misleading full-JD file.
- Unit coverage exists for slugging, metadata rendering, idempotency, and conflict handling.
